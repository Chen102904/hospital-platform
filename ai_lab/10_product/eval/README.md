# 端到端评测

近 40 道题，从「问题」进去到「回答」出来，中间怎么走的完全不管——只看最后那段人话对不对。

## 为什么单独做这一套

`../tests/check_all.py` 那 87 项测的是**代码没坏**：HTTP 200、记录落库、状态是 `ok`、工具被调用了、耗时大于 0。

它们全都通过的时候，模型把 `1159.40` 说成别的数、把「内科」说成「儿科」、把没有的数据编出来——**87 项依然全绿**。

| | check_all.py | 本目录 |
|---|---|---|
| 问的问题 | 代码还能跑吗 | 答得对吗 |
| 判据 | 状态码 / 数据库行数 / 函数返回值 | 回答里的事实 |
| 判错的后果 | 白盒可见，改代码时立刻发现 | 用户看到错误答案，还以为系统没问题 |

两套都要有。前者防止你改坏，后者防止你一直错着还自我感觉良好。

## 三个文件

| 文件 | 作用 |
|---|---|
| `cases.json` | 题库。题目、期望、出题意图都在里面 |
| `run_eval.py` | 取真值 → 逐题跑 → 判分 → 出报告 |
| `reports/` | 产物。每次跑生成一份 `.md`（给人看）和一份 `.json`（给程序看） |

## 怎么跑

在 `10_product/eval` 目录下，或者从任何地方写全路径：

```bash
PY="C:/Users/dell/.workbuddy/binaries/python/envs/default/Scripts/python.exe"

$PY run_eval.py --truth        # 只打印真值，不调模型、不花钱
$PY run_eval.py --limit 2      # 只跑前两题，确认链路通
$PY run_eval.py                # 全量（跑完整个题库）
$PY run_eval.py --only A01,F01 # 指定题号
$PY run_eval.py --cat 查文档    # 只跑某一类
$PY run_eval.py --tag before-fix   # 给这次跑分打标签，方便对比改动前后
$PY run_eval.py --retries 3 --backoff 30   # 接口不稳时多等几轮（额度耗尽时没用）
```

PowerShell 里记得写成 `& $PY run_eval.py`（和项目里其他地方一样）。

退出码：准确率低于 80% 时返回 1，可以接进 CI 当门禁。

也可以用闯关器的入口（参数原样透传）：

```bash
$PY drill.py eval --truth
$PY drill.py eval --limit 2
$PY drill.py eval
```

## 实测：这套系统现在什么水平

2026-10-23，同一个模型连跑三轮，用同一套判分：

| 轮次 | 准确率 | 失败题 |
|---|---|---|
| 第 1 轮 | 33/37 = **89.2%** | B03 B04 E02 E03 |
| 第 2 轮 | 32/37 = 86.5% | B03 B04 **C09** E02 E03 |
| 第 3 轮 | 33/37 = **89.2%** | B03 B04 E02 E03 |

波动只有 1 道题（2.7 个百分点），稳定失败 4 道。

### 强在哪

| 维度 | 结果 |
|---|---|
| 该拒答的都拒了 | **8/8** — UPS 电池、WiFi 密码、院长是谁、服务器配置、营收目标、满意度调查 |
| 空结果没瞎编 | **4/4** — 近 7 天无收费、近 3 天无收费、库存低于 20 是 0 条、低于 5 是 0 条 |
| 引用都标了出处 | **9/9** |
| 工具路由 | **30/30** — 一次都没调错工具 |
| 收入类查询 | **6/6** — 含前五名、末位科室、指定科室、跨 60 天 |

安全相关的维度全是满分。这不是巧合：只读账号 + SQL 写死 + 工具白名单 + 阈值 + 出处，这几层是真的在起作用。

### 弱在哪：一个函数

4 道稳定失败的题，根因是同一个——**`low_stock_medicines` 这个工具的表达能力不对口**。

| 题 | 问什么 | 模型干了什么 | 问题在哪 |
|---|---|---|---|
| B03 | 哪个药库存最少 | 用默认阈值 20 查到空，然后建议用户「把阈值调**低**」 | 方向反了。库存最少的是 45，要调**高**才查得到 |
| E02 | 库存最少 + 为什么不许直改 | 同上，后半段答得完全正确 | 同上 |
| E03 | 库存最少 + 收入最高 | 同上，还老实说了句「我手头没这个工具」 | 同上 |
| B04 | 布洛芬还有多少 | 很聪明地把阈值调到 10000，但只拿到前 30 条 | **`MAX_ROWS=30` 截断**，480 盒在 58 种药里排不进前 30 |

不是模型笨，是**参数语义错位**：

- 参数叫 `threshold`（低于多少算告警），而用户问「库存最少」是**排序**语义，两者不是一回事
- 想覆盖到 45 和 480，阈值就得开得很大；一开大，结果超过 30 行又被截断

正确的修法不是写 prompt 教模型「记得把阈值调大」——那是拿提示词补工具的坑，换个模型就失效。应该给工具加一个真正对口的参数（比如 `order_by=stock_asc, limit=10`），或者干脆拆成「告警清单」和「库存排名」两个工具。

**这就是端到端评测最值钱的地方：它把「系统不太行」精确定位到了「一个函数的参数设计」。** 87 项单元测试跑一万遍也不会告诉你这件事。

### 按这个结论修完的结果

选了「拆成两个工具」，没选「加参数」——因为参数一多，模型还是要猜什么时候用哪个语义，而两个名字天然就把语义分开了。

新增 `medicine_stock(name, order, limit)`：`name` 缺省时按 `order` 排序取前 N（点查「最少/最多」），传 `name` 时按名字模糊查（点查「某个药剩多少」）。`low_stock_medicines` 保留，退回纯告警语义，并在 0 行时补一句 note 指路。

| 题 | 修之前 | 修之后 |
|---|---|---|
| B03 哪个药库存最少 | 猜阈值，答「查不到」 | `medicine_stock(order=asc, limit=1)` → 地塞米松 45 支 |
| B04 布洛芬还剩多少 | 阈值调到 10000，被 30 行截断 | `medicine_stock(name="布洛芬")` → 480 盒 |
| E02 库存最少 + 为什么不许直改 | 前半段答不上 | 两个工具都调，数字 + 出处齐全 |
| E03 库存最少 + 收入最高 | 同上 | 两个查库工具都调，两个数都对 |
| B05 库存最多是哪个（新增） | — | `order=desc` → 葡萄糖 720 瓶 |

5 题一次全过。但**别以为这就完了**——那一轮 38 题里另外冒出 3 题失败，其中 2 题是判分漏、1 题是系统真 bug（模型返回空内容被当成成功）。详见上一节「判分自己也会骗人」和主 README 的「修完之后」。

**工具修好只是把这一层堵上，下一层立刻露出来。** 这就是为什么这件事要一轮一轮跑，而不是修完一个工具就说「搞定了」。

### 修完之后的完整一轮（以及一个没跑完的教训）

修完工具、空回答、判分三处之后又跑了一轮，跑到第 31 题时接口开始返回 `HTTP 403 AccessDenied.Unpurchased`——额度耗尽，剩下 6 题全部 0.2 秒内失败。

按已测到的 32 题算：

| 指标 | 结果 |
|---|---|
| 准确率 | **31/32 = 96.9%** |
| 未测到 | 6 题（E02 F01 F03 F04 F05 F06） |
| 正确拒答 | 6/6 |
| 误拒 | 0 |
| 工具命中 | 27/27 |
| 引用标注 | 9/9 |
| 唯一真失败 | D05（药品批号/近效期，撞上 6 轮上限，单题烧 27824 tokens） |

如果当时没加「未测到」剔除，报告会写 31/38 = 81.6%，看起来像全面退化。**那个数字是假的**——详见下面「『未测到』为什么必须从分母里剔出去」。

D05 这一条留着没修：它问的东西在文档里属于「有意不做」清单，检索找不到正向答案，模型就一直换词重搜，6 轮下来上下文滚到 2.8 万 token。修法是给工具结果做体积预算或按轮次压缩早期结果，但**那天额度已经耗尽，没法验证改完是否真的有效**——按项目一贯的规矩，改完不能验证的就不改，先记在「还没做的」里。

## 判分自己也会骗人

第一轮跑完是 78.4%。我以为是系统真的不行，逐条看原文才发现：**有 4 题模型答对了，是我的判分判错了。**

| 题 | 模型写的 | 我的判据 | 为什么漏掉 |
|---|---|---|---|
| A06 | `**9** 张收费单` | 子串「9张」 | 加粗标记把 9 和 张 隔开了 |
| B01 | `没有库存低于 20 的药品` | 子串「没有低于」 | 中间插了「库存」两个字 |
| D01 | `文档里没找到` | 子串「没有找到」 | 少一个「有」 |
| F03 | `没有库存低于 5 的药品` | 同上 | 同上 |

跑第二轮又冒出两处：「没有明确提到」里的「没提到」不连续、「并没有做」里的「没做」不连续（中间隔着个「有」）。

修完工具、又跑一轮，还冒出两处，而且都是**同一类新变种**：

| 题 | 模型写的 | 我的判据 | 为什么漏掉 |
|---|---|---|---|
| B01 | `库存低于 20 的药品一个都没有` | 「没有低于」等 6 条正则 | 量词「一个」把「没有」和「低于」拆开了，12 字窗口够不着 |
| F01 | `近 7 天没有科室收入数据` | 同上 | 「没有」和「数据」中间隔着「科室收入」四个字 |
| D02 | `WiFi 密码这类信息不在我的服务范围内` | 只认「不知道 / 没有 / 查不到」 | 这是**划边界式拒答**，比「我不知道」更常见，一条正则都没覆盖 |
| A06 | `我手头的工具…没法直接给你收费单数量` | 同上 | 同一类漏判，而且它会让**误拒率漏统计**（显示 0 误拒，实际有 1 题） |

五次加上这四次，已经九次误判了。规律很清楚：**每加一类新问法，判分器就会被撞出一个新口子。** 这不是判分写得糙，而是「判断一句话有没有表达某个意思」本身就是开放的——所以每次跑完都必须逐条看失败原文，不能只看百分比。

结论：**中文的固定子串判据非常脆**。现在全部改成正则，并加了 `must_any_re` 字段专门给自由表述留口子。

这件事和第 7 步「金标准标窄导致结论反转」是同一类教训：**测量工具本身也要被测量。** 如果不逐条看回答原文，你只会看到一个难看的数字，然后跑去改根本没错的地方。

改判分的正确做法也记一下：**不要重跑，用 `--rerender` 拿同一批答案重新量**。重跑会让「分数变了」混进模型随机性，你就分不清是判分修好了还是运气好了。

## 题库怎么维护

### 加一题

```json
{
  "id": "A07",
  "cat": "查库·收入",
  "q": "上个月骨科收了多少？",
  "expect_tools": ["dept_revenue_rank"],
  "must_num": ["${BONE_AMT}"],
  "why": "换成指定科室、指定月份，测它会不会自己换算天数"
}
```

`why` 字段别省。半年后你自己看报告，只有它能告诉你「这题当初是想测什么」。

### 占位符：为什么不能把数字写死

题库里所有形如 `${TOP1_AMT}` 的值，都是在**跑分前**由 `build_truth()` 连库算出来再替换的。

原因很直接：演示数据的时间窗口是绕「今天」滚动的，你今天写死 `1159.40`，明天数据一变，整套题库就全错了——而报告会告诉你「准确率暴跌」，你以为是模型退化了，其实是题错了。

凡是来自数据库的数值，一律用占位符。只有文档里的静态事实（`scrypt`、`15 张表`、`不支持医保`）才写死。

### 判分字段

| 字段 | 含义 |
|---|---|
| `expect_tools` | 期望调用到的工具，**列出的必须全部调到**。早先按集合交集判（命中一个就算），E02/E03 这种双工具题只调一个也能过——是判分器自己的漏洞 |
| `must_num` | 答案里必须出现的数字，按浮点比较（容差 0.011）。金额用它——金额在库里唯一，顺带就把科室锁死了 |
| `must_text` | 必须全部出现的子串（已做全角转半角、去千分位、去空白归一化） |
| `must_any` | 至少出现一个，用于同义表述（不支持 / 不做 / 未实现） |
| `must_not` | 一个都不能出现，用于堵住典型错误 |
| `expect_no_data` | 期望回答「没有数据」。注意这和「拒答」不同：空结果是**正常回答**了问题 |
| `expect_refuse` | 期望拒答。问题超出知识库范围，正确行为是说不知道 |

`must_num` 优先于 `must_text`。比如「哪个科室收入最高」这题只断言 `1159.40` 就够了——这个金额在库里唯一，答对了金额就不可能答错科室。而如果去断言「内科」，会遇到「心血管内科」「神经内科」都包含「内科」的子串误判。

### 加占位符

在 `run_eval.py` 的 `build_truth()` 里加一条查询，返回的 dict 键名就是占位符名。注意**用独立写的 SQL，不要直接调工具函数**——两条路算出来结果不一致，说明工具实现的 SQL 有 bug，那比模型答错严重得多，必须在跑分之前就发现。

## 指标怎么看

| 指标 | 怎么算 | 掉了说明什么 |
|---|---|---|
| **准确率** | 断言全中的题 / **已测到的题** | 主指标。分母不含请求层失败的题，见下条 |
| 未测到 | 请求层就失败、模型没开口的题 | 涨 = 额度/限流/网络问题，**不是模型退化** |
| 正确拒答率 | 该拒的拒了 / 该拒总数 | 掉 = 开始编造了 |
| **误拒** | 本该能答却答成「我不知道」 | 涨 = 阈值调太严、prompt 写过头了 |
| 空结果识别 | 没数据时明确说没数据 | 掉 = 在空集上瞎补全 |
| 工具命中率 | 该调的工具调了 | 掉 = 路由判断错了 |
| 引用标注率 | 查文档题有没有标出处 | 掉 = 出处开始不标了 |

**正确拒答率和误拒必须一起看。** 只把检索阈值从 0.45 提到 0.55，第一个指标肯定涨，第二个也会涨——最后你把系统调成一个「什么都不肯说」的废物，而且从单个指标看它还在变好。

## 「未测到」为什么必须从分母里剔出去

这一条是踩出来的，不是想出来的。

有一轮 38 题跑到第 31 题，接口开始连续返回 `HTTP 403 AccessDenied.Unpurchased`，6 道题在 0.2 秒内 `status=error`。最初的版本把它们当「没通过」算进分母，报出 **31/38 = 81.6%**——这个数字是假的：那 6 道题模型一个字都没输出，根本没被测到。

拿这个 81.6% 去跟上一轮的 97.4% 比，你会得出「改坏了」的结论，然后跑去回滚根本没问题的改动。**这是测量工具第二次骗人**（第一次是中文子串漏判）。

现在分三层处理：

1. **单题退避重试**：`--retries 2 --backoff 20`，第 1 次失败等 20 秒，第 2 次等 40 秒。限流这种抖一下就好，重试能救回来。
2. **仍失败就标「未测到」**，从准确率、拒答率、工具命中率、分类通过率的分母里全部剔除，单独列一节并给出补跑命令。
3. **未测到超过 10% 就在报告顶部打红字**：这轮数据不可信，别跟别的轮次比。

重试用完还是 403，那就是额度真没了，只能换 Key 或充值，等也没用。

## 已知局限（别把这些当成「已经解决了」）

1. **期望值和工具共用同一套业务口径。** 虽然 SQL 是独立实现的，但如果对「收入」的定义本身就错了（比如漏了某个状态），两边会一起错。金额建议偶尔手工抽查一遍原始明细。
2. **关键词判分对同义表述不友好。** 已经用 `must_any` 兜了一部分（「第三」/「第3」/「3名」），但没见过的新说法还是会漏判。报告里每道失败题都附了回答原文，人工扫一眼就知道是真错还是判分太死板。
3. **端到端不测中间过程。** 模型可能根本没调工具、纯靠记忆答对了（比如「15 张表」），这题也会判过。所以工具命中率要单独看，别只看准确率。
4. **题库不到 40 题，样本偏小。** 单题波动就是 2~3 个百分点，所以别拿「这次 88% 上次 91%」当结论——要看具体是哪几题翻了，翻的那几题才是信息。
5. **跑一轮要十几万 token。** 实测 38 题约 20 万 tokens（含 D05 那种反复检索烧掉 2.8 万 token 一题的）。额度紧张时用 `--only` 分批跑，每批控制在 15 题以内。
